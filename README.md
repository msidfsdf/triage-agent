# triage-agent

给 FastGPT 这类产品做客服工单分诊：一条用户反馈进来，判断它是什么类型、能不能用知识库作答，
答不了就转人工。知识库来源是 FastGPT 官方文档，测试工单是它 GitHub 上的真实 issue。

## 它做什么

```
工单进来
  → 检索知识库（BM25，取 top5）
    → 模型判断：片段够不够答
      → 够：答，并标出依据的知识编号
      → 不够但缺关键信息：反问版本号 / 报错原文 / 部署方式
      → 完全没依据：转人工，不猜
```

三条路的输出都是结构化的（分类 / 决策 / 回复 / 理由 / 依据片段），可以直接展示，也可以批量跑评测。

## 怎么跑

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# 1. 先填 .env（参考 .env.example）
# 2. 抓数据：知识库 + 测试工单，约 1 分钟
python ingest.py

# 3. 起服务
uvicorn app:app --reload
```

打开 http://127.0.0.1:8000/ ，粘贴一条反馈，或者点「随机来一条真实工单」。

不想起服务也能直接试检索：

```bash
python kb.py
```

## 文件

| 文件 | 作用 |
|---|---|
| `ingest.py` | 抓 FastGPT 文档（切块）和已关闭 issue，写到 `data/` |
| `kb.py` | 知识库检索：jieba 分词 + BM25 |
| `triage.py` | 分诊：LangGraph 状态图（模型判断 → 检索 → 再判断 → 收尾） |
| `app.py` | FastAPI：`/triage`、`/random_ticket`、`/stats` |
| `decisions.md` | 每一次返工和实验的记录，含失败的那次 |

`data/` 下的文件是 `ingest.py` 生成的，不进 git —— 数据可复现，没必要存。

## 已知的问题

这些不是"以后再说"，是现在就没做好的，写在最前面：

1. **检索 top1 只有 7/10**。中文短问句和文档措辞对不上（用户说"聊天没更新"，文档写"聊天才会更新"）。
   top5 能到 9/10，所以靠多给几条候选 + 模型自己挑来兜。换向量检索是下一步。
2. **没有转人工阈值**。现在完全靠模型自己判断"够不够"，没有用相似度分数做兜底。
3. **评测集还没建**。现在的 10 条查询是手工构造的，只够看方向，不够出结论。
4. **分类标签倾斜**。真实工单里 87% 是 `bug`，二分类的话无脑全猜 bug 就有 87% 准确率，指标会失真。

## 设计上的几个取舍

- **知识库用仓库里的 mdx，不用文档网站**。网站是 Next.js 客户端渲染，抓下来要扒 HTML；mdx 是原文，切分干净，还能给出可核实的 GitHub 链接作为引用来源。
- **只用文档，不用历史工单当答案来源**。历史 issue 里的解法可能是用户自己猜的、可能已过时。答案只能来自官方文档，这样"依据"才站得住。
- **检索不到就明说找不到**。提示词里写"不要幻觉"基本没用，写成"只能用给出的片段，片段没有就是不知道"，才能被检查。
- **先用 BM25 不用向量**。DeepSeek 没有 embedding 接口，多引一家服务商不值得；而且 BM25 是个更干净的基线，以后换向量时"提升了多少"能直接对比出来。
